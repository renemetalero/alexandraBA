GUIA PASO A PASO – CONECTIVIDAD PRIVADA AWS → ON-PREMISE → AZURE
Basada en los dos formularios compartidos:
1. Solicitud permisos EKS-DID DESA - VS
2. Solicitud de creación de regla FW V2 – NGFW Palo Alto

======================================================================
1. OBJETIVO
======================================================================

Habilitar la comunicación desde un workload alojado en AWS hacia un
servicio privado ubicado en Azure, utilizando la red On-Premise como
tránsito.

Flujo esperado:

AWS (EKS / EC2 / aplicación)
        |
        | HTTPS TCP/443
        v
Red corporativa / On-Premise
        |
        | Enrutamiento corporativo
        v
Azure VNet / API privada

IMPORTANTE:
Los dos formularios compartidos documentan principalmente la habilitación
de la comunicación desde AWS hacia la red On-Premise y las reglas de
firewall requeridas.

El tramo On-Premise → Azure debe existir previamente o ser validado con
Networking. Si no existe, se deberá gestionar adicionalmente el
enrutamiento/regla correspondiente hacia la VNet o Private Endpoint de
Azure.


======================================================================
2. INFORMACIÓN QUE SE DEBE OBTENER ANTES DE INICIAR
======================================================================

Antes de crear las solicitudes, confirmar:

AWS:
- Nombre de la cuenta AWS.
- AWS Account ID.
- Application Code.
- Servicio origen: EKS, EC2, Load Balancer, etc.
- CIDR/IP origen.
- Ambiente: Desarrollo, QA o Producción.

Azure / destino:
- Nombre de la API o servicio.
- FQDN/URL privada del servicio.
- IP privada destino, si aplica.
- CIDR o segmento de Azure destino, si la gestión se realiza por segmento.
- Puerto requerido, normalmente TCP/443.
- Ambiente destino.
- Confirmar que el servicio no es público.

Red:
- Confirmar la ruta AWS → On-Premise.
- Confirmar la ruta On-Premise → Azure.
- Confirmar resolución DNS privada si se utiliza un hostname.
- Validar si se requiere comunicación únicamente de salida o bidireccional.

======================================================================
5. VALIDACIÓN DEL TRAMO ON-PREMISE → AZURE
======================================================================

Los formularios compartidos no documentan en detalle el segundo tramo de
la comunicación.

Por lo tanto, antes de dar por completada la conectividad se debe solicitar
a Networking la confirmación de:

1. Existe ruta desde la red On-Premise hacia la VNet de Azure.
2. El CIDR de AWS no se superpone con el CIDR de Azure.
3. Existe ruta de retorno desde Azure hacia AWS/On-Premise.
4. El firewall permite TCP/443 hacia el destino.
5. Los NSG/Firewall de Azure permiten el tráfico proveniente del segmento
   corporativo esperado.
6. Si la API utiliza Private Endpoint, confirmar que el tráfico corporativo
   puede alcanzar la IP privada del Private Endpoint.
7. Si se utiliza un FQDN privado, confirmar resolución DNS desde AWS a través
   de la infraestructura corporativa.
8. Confirmar si el acceso debe configurarse por IP o, preferiblemente según
   estándar de Networking, por segmento CIDR.

7. PRUEBAS DESPUÉS DE IMPLEMENTAR
======================================================================

Desde el workload AWS validar:

1. Resolución DNS:
   nslookup <hostname-api-azure>

2. Conectividad al puerto:
   curl -vk https://<hostname-api-azure>

   o

   nc -vz <ip-destino> 443

3. Validar que la conexión no esté saliendo a Internet.

4. Validar respuesta HTTP de la API.

5. Validar logs de la aplicación.

6. Solicitar a Networking confirmación de que el tráfico está pasando
   por la ruta/firewall esperado.

7. Si falla:
   - revisar DNS,
   - rutas AWS,
   - firewall On-Premise,
   - ruta On-Premise → Azure,
   - NSG/firewall Azure,
   - ruta de retorno,
   - autenticación de la API.


======================================================================
8. CRITERIO DE ACEPTACIÓN GENERAL
======================================================================

"La conectividad se considerará habilitada cuando el workload autorizado
en AWS pueda resolver y consumir mediante HTTPS TCP/443 la API privada
ubicada en Azure, utilizando la red On-Premise como tránsito, con las
reglas de firewall, rutas y permisos correspondientes habilitados y sin
exposición de la API a Internet."


======================================================================
9. RESUMEN DE LAS DOS GESTIONES
======================================================================

GESTIÓN 1:
Demanda Interna / Permisos de Red
Objetivo:
Documentar origen, destino, ambiente, puerto y necesidad de comunicación,
y solicitar a Networking la habilitación correspondiente.

GESTIÓN 2:
Regla NGFW Palo Alto
Objetivo:
Crear la regla de firewall que permita el tráfico desde el segmento AWS
hacia el destino corporativo/Azure definido.

RESULTADO:
AWS → Red On-Premise → Azure API privada.

NOTA FINAL:
Los valores de IP/CIDR/FQDN del destino Azure deben ser confirmados por
Networking antes de enviar las gestiones definitivas. Los destinos
172.19.11.65 y 172.32.88.217 incluidos en los formularios corresponden
al ejemplo existente y no deben reutilizarse para una nueva API sin
validación.
